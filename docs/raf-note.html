参照を並列に渡し，共通の事例で選ぶ

過去の窓（参照事例）を凍結した Chronos-2 に見せて予測を良くしたい． 考えることは 2 つ，どう融合するかとどう選ぶかである． 融合は「共変量の行として並列に渡す」に決めた．連結では事例がほとんど読まれないからである． 選び方は，クエリごとの検索をやめて，全クエリ共通の many-shot セットを試している．

要約

主張状態根拠
融合は並列（共変量の行）にする確定 正解の未来を渡すと，並列は −49.4%，連結は −2.0%（2 節）
クエリごとの検索では届かない確定 文脈が近い窓は −0.3%．正解に近い窓なら −17.2% なので，選び方の問題（3 節）

1

問題：どう融合し，どう選ぶか

予測したい系列の履歴（クエリ）に加えて，同じ系列の過去の窓をいくつか「参照事例」として見せる． 事例 1 件は「文脈 96 点＋その続き 64 点」の窓である．やり方は 2 つの軸で決まる．

どう融合するかどう選ぶか
従来の RAF 事例を履歴の前に連結する クエリごとに，文脈が近い窓を数件検索する
このノートの提案 事例を共変量の行として並列に渡す 全クエリ共通のセットを数十〜数百件渡す

並列に渡す発想自体は新しくない．Chronos-2 の技術報告（arXiv:2510.15821）も， group attention を検索拡張に使う可能性を今後の課題に挙げている． 新しいのは，連結では事例が読まれず並列なら読まれることを示した点（2 節）と， 並列だからこそ可能になる many-shot・task-level の選び方（4 節）である．

2

融合：並列に渡す

どうやって渡すか

Chronos-2 に「事例」という入力は無い．入口は予測対象（target），過去だけ分かる共変量， 未来まで分かる共変量，カテゴリ共変量の 4 つだけである． そこで事例 1 件を「未来まで分かっている共変量」1 本として登録する． 事例の文脈 96 点は履歴の末尾にそろえて置き，手前は NaN（欠測）で埋める．事例の未来 64 点は，予測したい 64 点と同じ位置に置く． 

target            = クエリの履歴 2032 点
past_covariates   = { "ret0": [NaN × 1936, 事例0の文脈 96 点], …, "ret7": … }
future_covariates = { "ret0": 事例0の未来 64 点,               …, "ret7": … }

モデルの中では，各行が 16 点ずつのトークンに切られる（1 行 132 トークン）． 各層で，行の中を混ぜる time attention（横）と，同じ位置のトークンを行をまたいで混ぜる group attention（縦）が交互にかかる．

行過去 1〜121過去 122〜127未来 1〜4
target（クエリ）履歴履歴 空（ここを予測する）
ret0（事例 0）NaN（無視される）事例の文脈 事例の未来
ret1（事例 1）NaN（無視される）事例の文脈 事例の未来
要点 クエリの「未来 1 個目（1〜16 ステップ先）」は，group attention で事例の「未来 1 個目」を同じ位置で直接見られる． 事例の行で値があるのは 11 トークンだけなので，その分だけ計算すれば済む．事例を数百件並べても計算が軽い．

従来の連結と並べると次のようになる．

連結と比べる

同じ事例を両方の渡し方で比べた．「未来だけ正解」は，事例の文脈は検索した窓のまま，未来だけを正解に差し替えたもので， 「渡した未来をどこまで読めるか」の上限を測る診断である．

事例（K=8）並列連結
未来だけ正解（診断）0.2533（−49.4%）0.4906（−2.0%）
正解に近い窓（診断）0.4145（−17.2%）0.4927（−1.6%）
文脈が近い窓0.4991（−0.3%）0.4945（−1.2%）
MSE（参照なし比）．連結は履歴 2032 点を残したまま前に足し，事例ごとに区切り 16 点を挟む 正解の未来を渡しても，連結はほとんど良くならない．並列は大きく良くなる． 文脈が近い窓だけは連結がわずかに良いが，検索の質の差（正解に近い窓との差）が結果に届くのは並列だけである （並列 17.0%，連結 0.4%）．
分かったこと

連結では，事例の未来がほとんど読まれない．並列なら読まれる． 連結では事例の未来が「過去」の場所に置かれ，並列では予測したい 64 点の真上に置かれる．この置き場所の差である． 履歴の長さのせいではない．連結は履歴を削らずに前に足しているし，参照なしで履歴を 624 点まで削っても +2.7% しか悪くならない．

さらに連結には上限がある．履歴 2032 点だと，8192 点の文脈に入る事例は 35 件までである． 並列は行を増やすだけなので，many-shot は並列でしかできない．

注意：本来の使い方ではない

共変量の行は本来「電力需要と気温」のように同じ時刻に並走する別の系列のためのものである． 同じ系列の何ヶ月も前の窓を，いまと同じ時刻のものとして入れている．

3

クエリごとの検索では届かない

並列なら事例は読まれる．では従来どおりクエリごとに検索すればよいか． 同じ並列の容れ物で，選び方だけを変えた．

選び方（並列）MSEQL参照なし比
正解に近い窓 K=8（診断．実際には使えない） 0.41450.1758−17.2%
文脈が近い窓 K=8（従来の RAF の検索）0.49910.1921−0.3%
直前の窓 K=4（recency）0.49780.1911−0.6%
参照なし0.50070.1887—
プラセボ K=4（クエリと同じ平均・分散の雑音）0.52320.1999+4.5%
正解に近い窓を引ければ大きく効くが，実際に使える検索はほぼ効かない プラセボは悪化するので，「行を足すだけで良くなる」副作用ではない．

文脈が似ている窓の未来は，クエリの未来とあまり似ていない（OT チャネルで順位相関 +0.12）． クエリごとに「正解に近い未来を持つ窓」を当てるのは，未来を予測するのと同じくらい難しい． これまで encoder や多様性の工夫を試したが，どれも recency を超えられなかった．

4

選択：全クエリ共通の many-shot セット

そこで問題の置き方を変える．クエリごとに正しい事例を当てるのをやめて， よく選んだ事例のライブラリを全クエリに渡し，どれを使うかは group attention に任せる． many-shot ICL の LLM 研究（Zhang et al., ACL Findings 2025）の考え方を取り入れている．

many-shot事例を数件ではなく数十〜数百件渡す．並列なら計算が軽い
task-levelチャネルごとに train の窓から 1 セットを選び，test の全クエリに同じセットを渡す．クエリごとの検索はしない
選び方ランダム，k-means の代表，Best-of-N（ランダムな 5 セットを train で試して最良を取る）． 勾配に基づく選び方（CLG）は後回し

途中の結果

val（全 7 チャネル）MSE参照なし比QL
参照なし0.3967—0.1656
ランダムな共通セット K=8（5 seed 平均）0.3935 ±0.0030−0.8%0.1673
ランダムな共通セット K=32（5 seed 平均）0.3892 ±0.0024−1.9%0.1668
ランダムに選んでも，件数を増やすと MSE が下がる．QL はわずかに悪化 整理前のコードでの結果．K=128 / 256，test，選び方の比較はこれから．
確かめるべきこと

共通セットが効く理由が「事例の中から合うものを選んで読んでいる」のか， 「ありうる未来の値の分布を渡しているだけ」なのかで，主張の強さが変わる． セット内で事例どうしの未来を入れ替えて（文脈と未来の対応を壊して）悪化するかで見分ける．

実験計画と現在地

済E1 融合：並列と連結を同じ事例で比べる（2 節）
済E2 クエリごとの検索の限界：正解に近い窓・文脈が近い窓・recency・プラセボ（3 節）
一部E3 many-shot：ランダムな共通セットで K = 8 / 32 / 128 / 256．val の K=8 / 32 のみ済
未E4 選び方：同じ K で，ランダム・k-means・Best-of-N を比べる．クエリごとの検索（文脈が近い窓）とも比べる
未E5 何が読まれているか：共通セット内で未来を入れ替える
未E6 再現：ETTh1 以外のデータセット

K などのハイパーパラメータは val で決め，その値で test を出す．

コマンド（codes/run.py，評価は codes/evaluate.py）
参照なし --select none／共通セット --select random|kmeans|bestofn --top-k 128
クエリごとの検索 --select l2|oracle|recent|placebo／連結 --fusion concat
未来の入れ替え --ablation shuffle-future／未来だけ正解 --ablation truth-future

事例の候補は 8 点間隔の窓．共通セットは train の窓から，クエリごとの検索はクエリの文脈より前に終わる窓から選ぶ． 整理前の実験の記録は git 履歴（c66158c 以前）と results/_archive/ にある．
