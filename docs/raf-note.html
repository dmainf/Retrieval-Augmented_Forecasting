検索の上限を測る

過去の似た窓（事例）を Chronos-2 に見せると予測は良くなるのか． ここまでに分かったのは 3 つ．事例は「並列」に渡せば効き，「連結」では効かない． ただし効くのは良い事例を渡せたときだけで，いまの検索器はそこに届いていない． このノートは，やったことを順に並べて，次の方針を決めるための材料にする．

要約

ここまでで分かったこと

問い答え根拠
Chronos-2 に事例の入口はあるか 無い 共変量の入口を借りて，事例を別の行として並べている（1 節）
並列に渡すと参照は効くか 効く 正しい事例なら誤差が半分になる（−49〜56%）（2 節）
いまの検索器で効くか ほぼ効かない 文脈の似た窓を引くと −0.3%．参照なしとほぼ同じ（2 節）

1

事例をどうやって渡しているか

Chronos-2 には「事例」という入力は無い．入口は次の 4 つだけである．

target予測したい系列（ここではクエリの履歴 2032 点）
past_covariates過去だけ分かっている別の系列
future_covariates未来の値まで分かっている別の系列（例：天気予報，祝日）
cat_covariateカテゴリ値の共変量

そこで事例 1 件を「未来まで分かっている共変量」1 本として登録する． 事例の文脈 96 点を履歴の末尾にそろえて置き，その手前は NaN（欠測）で埋める． 事例の未来 64 点は，予測したい 64 点と同じ位置に置く．実際に渡しているのは次の辞書である （codes/raf_model.py の parallel_inputs）． 

target            = クエリの履歴 2032 点
past_covariates   = { "ret0": [NaN × 1936, 事例0の文脈 96 点], …, "ret7": … }
future_covariates = { "ret0": 事例0の未来 64 点,               …, "ret7": … }

モデルの中で起きること

各行は 16 点ずつのトークンに切られる．1 行は「過去 127 個＋区切り（REG）1 個＋未来 4 個」の 132 トークンになる． 各層で 2 種類の注意が交互にかかる．

横time attention：1 つの行の中でトークンどうしを混ぜる
縦group attention：同じ位置にあるトークンを，行をまたいで混ぜる
行過去 1〜121過去 122〜127REG 未来 1〜4
target（クエリ）履歴履歴— 空（ここを予測する）
ret0（事例 0）NaN（無視される）事例の文脈— 事例の未来
ret1（事例 1）NaN（無視される）事例の文脈— 事例の未来
要点 クエリの「未来 1 個目（1〜16 ステップ先）」は，group attention で事例の「未来 1 個目」を同じ位置で直接見られる． 連結でも cross-attention でもない．group attention は行どうしの self-attention である．

従来の RAF は事例を時間軸に連結していた（事例を履歴の前に並べる）．下の図で両者を比べる．

これは本来の使い方ではない

共変量の行は本来「電力需要と気温」のように同じ時刻に並走する別の系列のためのものである． そこに同じ系列の何ヶ月も前の窓を，いまと同じ時刻のものとして入れている． Chronos-2 の論文も，こういう使い方は想定していない．

2

並列に渡すと参照は効く．ただし良い事例なら

「渡し方が悪いのか，事例の選び方が悪いのか」を分けるために，事例の質を 3 段階にした． A と B は答えを使うので実際には使えない．上限を知るためだけの診断である．

Aクエリ自身の文脈＋正解の未来をそのまま事例にする．完璧な参照
B正解の未来にいちばん近い過去の実在の窓を引く．検索がうまくいった場合の上限
Cクエリの文脈にいちばん近い窓を引く（生値の L2 距離）．実際に使える普通の検索
事例として入れるもの MSEQL参照なし比
Aクエリ自身＋正解（K=8） 0.22270.1268−55.5%
A同上（K=1） 0.25410.1347−49.3%
B正解に近い実在の窓（K=8） 0.41450.1758−17.2%
C文脈が近い窓（K=8） 0.49910.1921−0.3%
対照recency：直前の窓をそのまま（K=4） 0.49780.1911−0.6%
基準参照なし 0.50070.1887—
対照プラセボ：クエリと同じ平均・分散の雑音（K=4） 0.52030.1996+3.9%
55.5% の伸びしろが 3 段に分かれる A → B の 38 ポイントは「過去に正解そのものは無い」ことによる損． B → C の 17 ポイントは検索器の失敗．C と参照なしの差は 0.3 ポイントしかない．
読み方

渡し方（並列）には問題が無い．正しい事例なら 1 件でも誤差が半分になる． 効かないのはいまの検索器が良い事例を引けていないからである． プラセボは悪化するので，「行を足すだけで良くなる」副作用でもない．

検索をどれだけ良くすれば効き始めるか

検索の鍵に正解の未来を割合 a だけ混ぜて，検索の質を少しずつ上げた． a=0 は「一度予測して，その予測を鍵に検索する」実際に使える手法で， a=1 は B と同じである．

a：鍵に混ぜた正解の割合MSEQL

0.1250.49790.1897
0.250.48360.1873
0.50.45430.1823
0.750.42770.1779
1.0（＝B）0.41450.1758
ほぼ直線 検索の質を上げた分だけ，比例して良くなる．「ほぼ正解のときだけ効く」という崖ではない． 参照なし（0.5007）を下回るのは a ≈ 0.09 から．−5% には a ≈ 0.31，−10% には a ≈ 0.54 が要る．

ただしこの混ぜ方は「正解へまっすぐ近づける」特定の道筋なので，実際の検索器の改良が同じ直線に乗る保証はない． また a=0 の 0.5092 は C の 0.4991 より悪いので，出発点は C のほうである．

3

連結と比べる

同じ事例を，従来の RAF と同じく時間軸に連結して渡した．連結は 2 通り試した．

そのまま履歴 2032 点を残して，その前に事例を足す
削る全体を 2032 点に収めるため，事例の分だけ履歴を削る（K=8 なら履歴は 624 点）

「未来だけ正解」の行も足した．事例の文脈は検索した窓のまま，未来だけを正解に差し替える． 文脈が一致していなくても未来を読めるかを見るためである．

事例並列連結・そのまま連結・削る
未来だけ正解（K=8） 0.2533（−49.4%）0.4906（−2.0%）0.4881（−2.5%）
B：正解に近い窓（K=8） 0.4145（−17.2%）0.4927（−1.6%）0.5097（+1.8%）
C：文脈が近い窓（K=8） 0.4991（−0.3%）0.4945（−1.2%）0.5015（+0.2%）
プラセボ（K=4） 0.5203（+3.9%）0.4986（−0.4%）0.5061（+1.1%）
A：クエリ自身＋正解（K=1） 0.2541（−49.3%）0.4629（−7.5%）0.4831（−3.5%）
A：クエリ自身＋正解（K=8） 0.2227（−55.5%）0.3004（−40.0%）0.1028（−79.5%）
MSE（参照なし 0.5007 比）．連結の区切りは qmean，nan でも同じ結論 正解の未来を渡しても，連結は 2% しか良くならない．並列は 49% 良くなる．

A の K=8 だけは連結が大勝ちするが，見かけである．A では事例の文脈がクエリの末尾と完全に同じで， それが 8 回並ぶ．連結はこれを周期として延ばしているだけで，K=1 だと −3.5%， 文脈を検索した窓に戻すと −2% まで落ちる．

分かったこと

連結は，クエリと完全に一致する事例の続きしか写せない． 並列は，文脈が一致していなくても予測区間の上に置かれた未来を読む． 検索で引けるのは「似ているが一致しない」窓なので，使えるのは並列である．

渡し方を比べるときの上限には，A ではなく「未来だけ正解」を使う．

履歴を削るから効かないのではない

参照なしで履歴だけを 1856 / 1328 / 624 点に削っても，損は +0.4% / +1.9% / +2.7% と小さい． そして履歴を削らない連結でも，正解の未来を渡して −2% にとどまる． 連結が効かない原因は履歴の長さではなく，事例の未来の置き場所である． 連結では未来が「過去」の場所に置かれ，並列では予測したい 64 点の真上に置かれる．

なお，実際に使える C だけなら連結・そのまま（−1.2%）が並列（−0.3%）をわずかに上回る． ただし連結はプラセボでも −0.4% なので，中身を読んだ結果とは言えない． 検索の質の差が結果に届くのは並列だけである（B と C の差：並列 17.0%，連結 0.4%）．

4

並列に渡す方法は新しいか

アイデアそのものは新しくない．近いものが既にある．

Chronos-2技術報告（arXiv:2510.15821）の結論で， 「系列を埋め込みでグループ化すれば retrieval-augmented forecasting に使えるかもしれない」と今後の課題に挙げている
TimeRAF検索した系列をチャネル方向で統合する（Channel Prompting）．ただし学習する専用モジュールを使う
RAEF など2026 年の RAF 系（RAEF，Everglades の水位予測）は今も連結． KG-Chronos-2 は予測を出したあとで混ぜる事後融合

こちらの違いは，同じ系列の過去の窓を末尾にそろえて置き，その未来を「未来まで分かっている共変量」として予測区間に載せること， そしてモデルを一切学習しないことである．見つけた範囲では，この形で測った例は無かった． 新規性を言うなら，方法そのものより「連結は完全一致しか写せず，並列は近い事例の未来を読める」という 3 節の発見のほうである． 網羅的に調べたわけではないので，Chronos-2 の被引用論文は確認が要る．

5

共通の事例セットを試し始めた（保留中）

ここまではクエリごとに事例を選んでいた．別の方向として， Zhang et al.「Selecting Demonstrations for Many-Shot ICL via Gradient Matching」（ACL Findings 2025）の考え方を持ち込もうとした． 取り入れたいのは次の 3 つである．

many-shot事例を数件ではなく数十〜数百件渡す
task-levelクエリごとに選ばず，全クエリに同じセットを渡す（チャネルごとに 1 セット）
CLGセットの選び方．下で説明する

CLG（Curriculum Latent Gradient）を平たく言うと

1「学習できる架空の事例」を 8 本用意し，Chronos-2 は固定したまま， train で予測が良くなるように架空の事例だけを学習する
2学習の各段階で，train の窓 1 つ 1 つが架空の事例を「どちら向きに動かそうとするか」（勾配）を記録する
3train 全体の平均的な動かし方と同じ動かし方をする少数の窓を選ぶ． 「train 全体で学習したのと同じ効果を，選んだ少数の事例で出す」ことを狙う

うまくいく筋書きは，事例をたくさん並べておけば，group attention がクエリに合う事例を自分で選んでくれる，というものである． 心配な点もある．以前，上位 K 件の中で事例の未来を入れ替えても +0.9% しか変わらず， 「どの文脈にどの未来が付いていたか」はあまり使われていなかった．もし本当に使われないなら， 共通セットは「ありうる未来の値の集まり」にしかならず，効果は小さい．

作ったもの

sparse_rows.py事例の行のうち値のある 11 トークンだけを計算する Chronos-2 の計算． 元の計算と一致する（最大誤差 1.3e-4，値の規模 49）．参照なし 0.5007 も完全に再現． 事例 32 件で 1 チャネル 17 秒と速く，勾配も取れる
taskset.pyチャネルごとの固定セットを全クエリに渡して評価する（ランダム，k-means，ファイル指定）
clg.py架空の事例の学習，CLG 勾配の記録，勾配マッチングでの選択，Best-of-N

6

現在地と，決めること

確定事例は並列に渡す．連結は完全一致しか写せない
確定正しい事例なら誤差が半分になる．渡し方に問題は無い
確定過去に正解そのものは無いので，検索の上限は −17%（B）
確定いまの検索器（文脈が近い窓）では −0.3%．上限との差 17 ポイントが手つかず
確定検索の質を上げた分だけ比例して良くなる． 鍵を正解へ 1 割近づければ参照なしを下回る
途中全クエリ共通のランダムなセットで −1.9%（val，K=32）．CLG で選ぶと上積みできるかは未確認

方針の候補

案 1クエリごとの検索器を良くする． B と C の差 17 ポイントを取りにいく．目標は「鍵を正解へ 1 割以上近づける」こと． これまで encoder や多様性の工夫はどれも recency を超えられていない
案 2全クエリ共通の many-shot セットを CLG で選ぶ． 実装は済んでいて，残りは計算時間（全チャネルで数時間）． ランダムでも −1.9% 出ているので，その上に積めるかが焦点
案 3両方を同時に渡す． 共通セットとクエリごとの数件を一緒に並べる（論文 4.8 節）．案 1 か案 2 が動いてから
共通他のデータセットで再現する．K などは val で選んでから test を出す
