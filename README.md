# Retrieval-Augmented Forecasting

検索した窓をクエリ文脈の前に**そのまま連結**して，凍結した Chronos-Bolt で予測する．
オフセット整合なし，窓ごとの再正規化なしの，最小構成の RAF．

```
入力 = [ x_k | y_k ] SEP ... [ x_1 | y_1 ] SEP [ query ]
         \_______/               \_______/         \_____/
        k番目に似た窓            最も似た窓      予測したい文脈
```

SEP は事例の切れ目に挟む区切り（既定 `nan`，長さはバックボーンのパッチ長16）．
`--separator none` で純粋な連結になる．

学習は行わない（学習パラメータはゼロ）．`predict.py` は予測値と実測値の表だけを出し，
指標は `evaluate.py` に分けてある．

## 構成

| ファイル | 役割 |
|---|---|
| `codes/arguments.py` | 全ハイパーパラメータの定義 |
| `codes/dataset.py` | parquet読込・train/val/test分割・チャネル単位の窓切り出し |
| `codes/retriever.py` | 検索．encode / pool / select の3軸に分けてある |
| `codes/raf_model.py` | 検索窓の連結 + 凍結 Chronos-Bolt |
| `codes/predict.py` | 実行エントリ |
| `codes/encoder.py` | 未来で教師付けした対照学習による窓エンコーダの学習 |
| `codes/evaluate.py` | チャネル正規化 MSE |
| `codes/diagnose_retrieval.py` | 文脈類似度が未来類似度の代理になっているかの診断 |

## 準備

```bash
pip3 install torch transformers chronos-forecasting faiss-cpu numpy pandas pyarrow
```

データは `Datasets/_parquet/<dataset>.parquet`（`date` 列 + 各変数の列）．
バックボーンは初回実行時に Hugging Face から取得される．

## 実行

```bash
python3 codes/predict.py                        # ETTh1, seq96/pred64, k=1
python3 codes/predict.py --top-k 0              # 参照なしのベースライン
python3 codes/predict.py --dataset weather --top-k 12
python3 codes/predict.py --help                 # 全引数
```

主な引数（すべてデフォルトあり）：

| 引数 | 既定 | 意味 |
|---|---|---|
| `--dataset` / `--channels` | `ETTh1` / 全列 | 対象データと列 |
| `--seq-len` / `--pred-len` | `96` / `64` | クエリ文脈長と予測長（pred_len ≤ 64） |
| `--top-k` | `1` | 連結する検索窓の数．`0` で参照なし |
| `--retrieval-metric` | `euclidean` | キー間の距離．既定は生値のL2 |
| `--encoder` | `raw` | **軸1 encode**：`raw` / `zscore` / `spectral` / `learned` / `predicted` / `future`(オラクル) |
| `--encoder-path` | — | `--encoder learned` のチェックポイント |
| `--retrieval-rounds` | `1` | `--encoder predicted` の反復回数 |
| `--key-dim` | `0` | キーをPCAで落とす次元．`0` で射影なし |
| `--pool` | `all` | **軸2 pool**：`all` / `topm` / `cluster` |
| `--pool-size` / `--n-clusters` | `100` / `8` | 候補プールの大きさ，k-means のクラスタ数 |
| `--selector` | `topk` | **軸3 select**：`topk` / `mmr` / `dpp` / `eopt` |
| `--diversity` | `0.5` | 0 = 関連度のみ，1 = 多様性のみ．`topk` では未使用 |
| `--concat-order` | `nearest-last` | 最も似た窓をクエリの直前に置く |
| `--separator` | `nan` | 事例の切れ目を埋める値．8種（下記） |
| `--separator-len` | `0` | 区切りの長さ．`0` はパッチ長(16)に自動追従 |
| `--eval-stride` | `0` | テスト窓のずらし幅．`0` は窓長（非重複） |
| `--retrieval-stride` | `1` | 検索DBを作る窓のずらし幅 |

`--top-k` の上限は `(context_length - seq_len) // (seq_len + pred_len + separator_len)`．
既定値では 11（`--separator none` なら 12）．超えるとエラーで止まる（黙って切り詰めない）。

### 区切りについて

事例の切れ目に何を挟むか．8 種あり，「観測を捏造するか」で 2 つの圏に分かれる．

| `--separator` | 挟む値 | 観測の捏造 |
|---|---|---|
| `nan` | 欠測（Chronos が mask=0 として扱い，注意から外す） | **しない** |
| `none` | 何も挟まない（純粋な連結） | しない |
| `mean` | 入力全体の平均 | する |
| `qmean` | クエリ文脈だけの平均 | する |
| `rmean` | 検索窓だけの平均 | する |
| `local` | そのギャップの隣接 2 値の中点 | する |
| `linear` | 隣接 2 値の線形補間（段差を消す） | する |
| `zero` | 定数 0 | する |

ETTh1 での比較（`--eval-stride 16`，チャネル正規化 MSE．K=0 の参照なしは 0.5842）：

| | K=1 | K=2 | K=4 | K=8 | K=11 | K=1→11 の増加 |
|---|---|---|---|---|---|---|
| `qmean` | 0.5901 | **0.6052** | **0.5999** | **0.5999** | **0.6051** | +0.0151 |
| `mean` | **0.5880** | 0.6099 | 0.6093 | 0.6154 | 0.6236 | +0.0356 |
| `rmean` | 0.5887 | 0.6129 | 0.6127 | 0.6179 | 0.6256 | +0.0369 |
| `local` | 0.5958 | 0.6239 | 0.6394 | 0.6485 | 0.6550 | +0.0592 |
| `linear` | 0.6034 | 0.6342 | 0.6527 | 0.6604 | 0.6647 | +0.0612 |
| `nan` | 0.6125 | 0.6212 | 0.6253 | 0.6275 | 0.6293 | +0.0168 |
| `none` | 0.6622 | 0.6948 | 0.7301 | 0.7249 | 0.7286 | +0.0665 |
| `zero` | 0.6736 | 1.0436 | 1.5021 | 1.5650 | 1.5786 | +0.9050 |

読み取れること：

- **`zero` が壊滅的**（K=8 で 1.57）。0 はデータの水準から遠いので Chronos の instance norm の
  `loc`/`scale` を歪め，K が増えるほど歪みが累積する。この軸で支配的なのは「境界の示し方」ではなく
  「バックボーンの統計を壊さないこと」だった。マーカー性が最大の条件が最悪なので，
  「境界を明示すると効く」という仮説は棄却される。
- **K 依存性が小さいのは `qmean` と `nan`**（+0.015, +0.017）。どちらも定義が K に依存しない。
  `mean` は K が増えるほど検索窓側に引っ張られるので，K を振る実験では交絡になる。
- **どの区切りでも K=0 には届かない**。区切りは「参照による害を打ち消す」ところまでで，
  「参照が有益になる」には至っていない。

既定は `nan`。性能では `qmean` がやや上回る（K=2 以降で最良）が，`nan` は**存在しない観測を
挿入しない唯一の変種**で，意味が K にも実装の選択にも依存しない。`qmean` との差 (0.590 vs 0.613)
は「捏造した観測を読ませることで得られる分」の見積もりになる。

## 検索の3軸

`retriever.py` は「どう表現するか」「どこから選ぶか」「どう選ぶか」を独立に振れる形にしてある．
既定の `raw / all / topk` が通常の最近傍検索で，これまでの RAF ベースラインと同一（数値も一致する）．

| 軸 | 選択肢 | 意味 |
|---|---|---|
| encode | `raw` | 文脈の生値 |
| | `zscore` | 窓ごとに標準化．水準とスケールを落とし形だけで照合する |
| | `spectral` | 中心化した文脈の `|rFFT|`．周期構造で照合し位相を無視する |
| | `learned` | `encoder.py` で学習した埋め込み．未来が似ている窓が近くなる空間 |
| | `predicted` | 2段階．参照なしで一度予測し，その**予測未来**をキーに DB の未来を検索する |
| | `future` | **オラクル**．真の未来をキーにする．実行不能な設定で，検索性能の上限を測るためだけにある |
| pool | `all` | 制約なし．DB 全体が候補 |
| | `topm` | 距離上位 `pool_size` 件．SARAF の候補プールにあたる |
| | `cluster` | クエリと同じ k-means クラスタの窓だけ．レジームの粗い代用 |
| select | `topk` | 最近傍 K 件 |
| | `mmr` | 関連度と多様性の貪欲トレードオフ（SARAF の選択器） |
| | `dpp` | DPP の MAP を貪欲近似．log det 最大化＝**D最適**（体積） |
| | `eopt` | `lambda_min(sum x x^T)` の貪欲最大化＝**E最適** |

`dpp` と `eopt` はクエリごとに M×M カーネルを作るので `--pool all` では動かない（明示的にエラーになる）．

`eopt` には注意が必要で，K 個のランク1行列の和はランクが高々 K なので，
**キー次元が K 以上だと `lambda_min` は恒等的に 0** になり基準として何も言っていない．
`--key-dim` を `--top-k` より小さくして初めて意味を持つ（満たさなければエラーで止まる）．

## 検索は効いていない．ただし検索器の問題である

`--encoder future` で「真の未来が最も近い窓」を引くと，検索器の性能上限が測れる．
ETTh1，`--eval-stride 16`，チャネル正規化 MSE（K=0 の参照なしは 0.5842）：

| 区切り | キー | K=1 | K=2 | K=4 | K=8 | K=11 |
|---|---|---|---|---|---|---|
| `qmean` | 文脈（通常） | 0.5901 | 0.6052 | 0.5999 | 0.5999 | 0.6051 |
| `qmean` | **未来（オラクル）** | 0.6130 | 0.5520 | 0.4888 | 0.4878 | **0.4825** |
| `nan` | 文脈（通常） | 0.6125 | 0.6212 | 0.6253 | 0.6275 | 0.6293 |
| `nan` | **未来（オラクル）** | 0.5823 | 0.5546 | 0.4873 | 0.4758 | **0.4700** |

- オラクルは K=0 を **19.5% 下回る**（0.4700 vs 0.5842）．
  したがって「凍結 Chronos への生連結」という注入方式は律速ではない．**検索の中身が律速**．
- **K に対する符号が逆転する**．文脈で引くと K を増やすほど悪化し，
  未来で引くと K を増やすほど改善する．事例追加はバリアンスを下げるがバイアスを増やす，
  という ICL 理論の予測どおりで，検索品質がその収支の符号を決めている．
- K=1 ではオラクルもほとんど効かない（0.5823）．1件の良い事例では足りず，
  効いているのは件数によるバリアンス低減のほう．

## 文脈類似度は未来類似度の代理になっているか

`diagnose_retrieval.py` が，バックボーンを介さずに検索そのものを測る．
全クエリ×全DB窓について文脈距離 `d_x` と未来距離 `d_y` を求め，
クエリ内での順位相関（Spearman）を取る．

```bash
python3 codes/diagnose_retrieval.py --dataset ETTh1 --metric correlation
```

ETTh1，チャネル平均：

| metric | Spearman(d_x, d_y) | OT（目的変数）単体 |
|---|---|---|
| `euclidean` | +0.729 | +0.884 |
| `cosine` | +0.672 | +0.265 |
| `correlation` | **+0.487** | **+0.123** |

生値の L2 では相関が高く見えるが，これはほぼ**水準の一致**を測っているだけで，
水準とスケールを落とす `correlation` にすると +0.487 まで落ち，
目的変数 OT に至っては +0.123 とほぼ無情報になる．
`exchange_rate` ではさらに極端で，文脈最近傍が未来距離の 98 パーセンタイル
（＝ほぼ最遠）に落ちるチャネルがある．

図は `results/diagnostics/` に出る．
A が順位散布図，B が top-1 の未来距離パーセンタイル分布，C が K に対する到達未来距離
（文脈 0.67×中央値 に対しオラクル 0.34×中央値 で，検索品質には約2倍の伸びしろがある）．

## 未来側で検索を決める

診断の結論は「文脈の近さは未来の近さを測れていない」だった．
ならば未来側で検索を決めればよいが，真の未来は使えない（それがオラクルが実行不能である理由）．
実行可能な代替が2つある．

**learned** — 文脈を「未来が似ている窓どうしが近くなる空間」に写すエンコーダを学習する．
入力は文脈だけなので推論時に使える．未来は学習の教師としてのみ現れる．

```
target_ij = pearson(y_i, y_j)       未来．学習時にしか見ない
pred_ij   = cos(f(x_i), f(x_j))     文脈．検索時に使う
loss      = KL(softmax(target/t) || softmax(pred/t))
```

正例を 0/1 で切らず連続値のまま扱う soft contrastive で，
FASCL（arXiv:2602.10711，クロスセクション株式検索）の損失を時間方向に向け直したもの．
文脈は窓ごとに z-score するので，生値 L2 が実質測っている「水準の一致」には逃げられない．

```bash
python3 codes/encoder.py --dataset ETTh1
python3 codes/predict.py --encoder learned --encoder-path checkpoints/ETTh1_enc.pt
```

学習は検索split しか触らない．val の Spearman が途中で頭打ちになり以後は
未学習ベースラインを下回るので，**ベスト重みを保存する**（stride 1 の窓は
8481 本あっても独立な標本は 8481/96 本程度しかなく，数百ステップで未来を覚えてしまう）．
ETTh1 で val Spearman +0.551（手作りの z-score は +0.513）．

**predicted** — 参照なしで一度予測し，その予測未来をキーにして DB の未来を検索する．
真の未来ではないので実行可能で，オラクルの「動く版」にあたる．

## 結果：予測未来での検索が唯一 K=0 を明確に下回る

ETTh1，`--eval-stride 16`，`--separator qmean`，チャネル正規化 MSE．
`*` は参照なし K=0（0.5842）を下回ったもの．

| encoder | K=1 | K=2 | K=4 | K=8 | K=11 |
|---|---|---|---|---|---|
| `raw`（従来） | 0.5901 | 0.6052 | 0.5999 | 0.5999 | 0.6051 |
| `zscore` | 0.6592 | 0.7755 | 0.6654 | 0.6161 | 0.5877 |
| `learned` | 0.6639 | 0.7079 | 0.6320 | 0.5966 | 0.5820* |
| **`predicted`** | 0.6535 | 0.5998 | **0.5706\*** | **0.5697\*** | **0.5670\*** |
| `future`（オラクル） | 0.6130 | 0.5520* | 0.4888* | 0.4878* | 0.4825* |

- `predicted` が K=11 で 0.5670．参照なしを **2.9%**，従来の `raw` を **6.3%** 下回る．
  raw とオラクルの差の **31%** を埋めたことになる．
- `learned` は `zscore` を全 K で上回るので対照学習そのものは効いているが，
  K=0 を割るのは K=11 のみ（0.5820）でわずか．
- **K 依存性の向きが encoder で変わる**．`raw` は K を増やすほど悪化し，
  `learned` と `predicted` は改善する．オラクルと同じ向きで，
  検索品質が「事例追加はバリアンスを下げバイアスを上げる」収支の符号を決めている．
- `predicted` に `--retrieval-metric correlation` を使うと大きく悪化する（K=4 で 0.7168）．
  予測未来の水準情報は捨てないほうがよい．

### 反復すると悪くなる

`predicted` の出力をさらに次の検索クエリにする（`--retrieval-rounds`）と，一貫して悪化する．

| 回数 | K=4 | K=11 |
|---|---|---|
| 1 | **0.5706** | **0.5670** |
| 2 | 0.5834 | 0.5795 |
| 3 | 0.5868 | 0.5787 |

2回目のクエリは，1回目に引いてきた窓に引きずられた予測である．
検索結果が次の検索を強化する正のフィードバックになり，最初に引いた事例に固着する．
**クエリは参照なしの予測から作るのがよい**．素の精度では K=0 のほうが劣るのに，
クエリとしてはそちらが優れているという逆転が起きている．

## pool 軸と select 軸：多様性は検索が下手なときだけ効く

`predicted` は encode 軸だけの変更だった．残る2軸を，予測未来の空間の上で振る．

### select 軸（K=11，`--pool topm --pool-size 100`）

| selector | w=0.1 | w=0.25 | w=0.5 | w=0.75 | w=0.9 |
|---|---|---|---|---|---|
| `topk`（多様性なし） | — | — | 0.5670 | — | — |
| `mmr` | — | 0.5674 | 0.5659 | 0.5647 | — |
| **`dpp`** | 0.5591 | 0.5568 | 0.5548 | **0.5546** | 0.5589 |
| `eopt`(key_dim 4) | — | 0.5651 | 0.5645 | — | — |

**`dpp` が最良で 0.5546**．参照なし（0.5842）を **5.1%**，従来の `raw/all/topk`（0.6051）を
**8.3%** 下回り，raw とオラクルの差の **41%** を埋める．
`mmr`（SARAF の選択器）はほとんど効かず，`eopt` も効かない．

注目すべきは **`dpp` > `eopt`** で，中間発表スライド13の目的関数は `eopt`（E最適，λ_min）
のほうである．体積（D最適）で選ぶほうが経験的に強い．

### pool 軸（`--selector topk`，`--pool-size 50`）

| n_clusters | 4 | 8 | 16 |
|---|---|---|---|
| cluster | 0.5678 | 0.5649 | 0.5753 |

k-means によるレジームプールは，効いても 0.5670 → 0.5649 とわずかで，クラスタを増やすと悪化する．
`dpp` と組み合わせても 0.5564 で，`topm` の 0.5546 を超えない．
**いまのところ pool 軸より select 軸のほうが効く．**

### 最も重要な所見：最適な多様性は検索品質で決まる

同じ `dpp` を encoder を変えて掛けると，多様性の効き方の符号が変わる．

| encoder | topk | w=0.1 | w=0.25 | w=0.5 | w=0.75 | w=0.9 | 最良 |
|---|---|---|---|---|---|---|---|
| `raw`（検索が下手） | 0.6051 | 0.5894 | 0.5840 | 0.5765 | **0.5734** | **0.5734** | w=0.75〜0.9 |
| `predicted`（中くらい） | 0.5670 | 0.5591 | 0.5568 | 0.5548 | **0.5546** | 0.5589 | w=0.75 |
| `future`（オラクル・完璧） | **0.4825** | 0.4875 | 0.4893 | 0.4924 | 0.4933 | 0.4937 | **多様性なし** |

- `raw` は多様性を上げるほど単調に改善し，13% 良くなって K=0 も下回る．
- `predicted` は改善するが幅が小さく（2.2%），w=0.9 で折り返す．
- **オラクルはどの多様性でも悪化する**（0.4825 → 0.4937）．

つまり多様性は，**関連度の順位が信用できないときのヘッジ**である．
順位が正しいなら，多様性のために関連度を手放すのは損でしかない．
検索が良くなるほど最適な多様性は下がり，完璧なら 0 になる．

これは SARAF の「データセットの定常性で多様性を変調する」の精緻化にあたる．
変調すべきは定常性ではなく**検索の信頼度**そのもので，そちらはオラクルとの差として直接測れる．

### K を振っても順序は変わらない

| | K=2 | K=4 | K=8 | K=11 |
|---|---|---|---|---|
| `predicted` + `topk` | 0.5998 | 0.5706 | 0.5697 | 0.5670 |
| `predicted` + `dpp` w=0.75 | **0.5862** | **0.5681** | **0.5636** | **0.5546** |

## まとめ：ここまでの最良構成

```bash
python3 codes/predict.py --eval-stride 16 --top-k 11 --separator qmean \
  --encoder predicted --pool topm --pool-size 100 --selector dpp --diversity 0.75
```

| 構成 | MSE | K=0 比 |
|---|---|---|
| 参照なし K=0 | 0.5842 | — |
| raw / all / topk（従来の RAF） | 0.6051 | +3.6% |
| raw / topm / dpp w=0.75 | 0.5734 | −1.8% |
| predicted / all / topk | 0.5670 | −2.9% |
| **predicted / topm / dpp w=0.75** | **0.5546** | **−5.1%** |
| future / all / topk（オラクル・実行不能） | 0.4825 | −17.4% |

## select 軸はまだ終わっていない（が，掴む手がない）

多様性の重み w をクエリごとに最適化できたら，という上限を測る．
既存の実行結果の per-row 誤差を組み替えるだけで，追加実行は要らない．

| encoder | 固定 w の最良 | クエリ毎に w を最適化 | 差 |
|---|---|---|---|
| `raw` | 0.5734 | 0.5111 | −10.9% |
| `predicted` | 0.5546 | **0.5003** | −9.8% |
| `future`（完璧な鍵） | 0.4825 | **0.4293** | −11.0% |

**鍵が完璧でも per-query w は 11% 効く．** 最良 w が `topk` だったクエリはオラクルでも 34% しかない．
したがって多様性は「検索の下手さのヘッジ」だけではなく，
**予測対象そのものが決まらないクエリへのヘッジ**でもある．w が追うべきは両者の合計．

ただしこの上限は真の未来で選んでおり，6 通りの最小値なので選択バイアスを含む．
観測可能な特徴だけで w を決めて分割検証すると：

| w の決め方 | MSE |
|---|---|
| 固定 w = 0.75 | 0.5546 |
| 予測の不確かさ q0.9−q0.1 | 0.5539〜0.5578 |
| 近傍の鋭さ d0/d10 | 0.5542〜0.5568 |
| 両者の積 | 0.5531〜0.5578 |
| **対照：無意味な乱数特徴** | **0.5572 ± 0.0016** |

**どれも乱数対照と区別がつかない．** 伸びしろは実在するが，安直な proxy では掴めない．
評価窓が 1239 本しかなく 1 セル 34 本程度なので統計的にも力不足で，
再挑戦するならまず `--eval-stride 1`（19,831 本）から．

## 鍵の精度と最終性能：`--oracle-mix`

`predicted` の鍵に真の未来を混ぜ，鍵の精度を連続的に動かす（診断専用）．

| 混合率 a | MSE | 0.125 あたり |
|---|---|---|
| 0.0（正直な predicted） | 0.5670 | — |
| 0.125 | 0.5491 | **−0.0179** |
| 0.25 | 0.5328 | −0.0163 |
| 0.5 | 0.5069 | −0.0130 |
| 0.75 | 0.4884 | −0.0093 |
| 1.0（オラクル） | 0.4825 | −0.0030 |

曲線は a=0 で最も急で，鍵が良くなるほど寝る．鍵への投資は今が最も効率が良い，
という読みで encode 軸に進んだ——が，次節でその前提が崩れた．

## 重要：ここまでのベースラインは弱すぎた

鍵を作る stage-1 の予測に，96 点ではなくもっと長い履歴を与える（`--stage1-context`）．
Chronos-Bolt の context_length は 2048 で，これまで 96 点しか使っていなかった．

| stage-1 文脈長 | 参照なし K=0 | predicted K=11 |
|---|---|---|
| 96 | 0.5842 | 0.5670 |
| 256 | 0.5548 | 0.5559 |
| 512 | 0.5286 | 0.5514 |
| 1024 | 0.5093 | 0.5556 |
| **2048** | **0.5029** | 0.5526 |

**履歴をそのまま長く読ませるだけの参照なしが 0.5029** で，
seq_len=96 での最良 RAF（0.5546）はもちろん，オラクル（0.4825）にも迫る．
`seq_len=96` の K=0（0.5842）は不当に弱いベースラインだった．

## 固定予算での比較：検索は履歴に勝てるか

文脈の予算は 2048 点で，検索窓を 1 つ入れるたびに履歴を
`win_len + sep_len = 176` 点捨てている．同じ予算で配分を変えて比べる
（`--query-context` で RAF 入力側の履歴長を seq_len から切り離した）．

| K | 履歴 | `raw` | `predicted` | `future`（オラクル） |
|---|---|---|---|---|
| 0 | 2048 | **0.5029** | — | — |
| 1 | 1872 | 0.5010 | 0.5014 | 0.4985 |
| 2 | 1696 | 0.5007 | 0.5014 | 0.4960 |
| 4 | 1344 | **0.5004** | 0.5027 | **0.4934** |
| 8 | 640 | 0.5138 | 0.5089 | 0.5019 |
| 11 | 112 | 0.5738 | 0.5718 | 0.5123 |

読み取れること：

- **検索で得られるのは 0.5029 → 0.5004，わずか 0.5%**．K=8 以降は履歴を削りすぎて損になる．
- **`predicted` の優位が消える**（0.5014 対 `raw` 0.5010）．
  鍵を良くする工夫は，履歴が短いときにだけ効いていた．
- **完璧な検索でも 0.4934，1.9% しか買えない**．
  seq_len=96 のときオラクルは 17.4% だったので，**上限が 17.4% → 1.9% に潰れた**．

検索DBを直近（val split）に替えても変わらない（K=2 で 0.5007 → 0.5010）ので，
DB の鮮度の問題ではない．

**結論**：`seq_len=96` で観測していた RAF の利得は，その大部分が
**文脈長のアーティファクト**だった．検索窓の連結は，要するに履歴を
バラバラな順序で読ませることをしていて，バックボーンは履歴を直接読むほうが遥かに上手い．
同じ文脈予算を与えたベースラインと比べると，検索が買えるものはほとんど残らない．

この対照実験は RAFT・TimeRAF・SARAF いずれも報告していない．

## 3データセットでの確認

ETTh1 が不適切なテストベッドだった可能性を潰すため，
性質の異なる `ETTm2`（15分粒度，強い周期）と `exchange_rate`（日次，ほぼランダムウォーク）
でも同じ固定予算比較を行った．

### まず文脈長だけを伸ばす（参照なし）

| 文脈長 | ETTh1 | ETTm2 | exchange_rate |
|---|---|---|---|
| 96 | 0.5842 | 0.5470 | **0.1595** |
| 512 | 0.5286 | 0.3872 | 0.1767 |
| 2048 | **0.5029** | **0.3633** | 0.1737 |
| 96→最良 | −13.9% | **−33.6%** | +8.9%（伸ばすと悪化） |

ETT 系は文脈を伸ばすだけで大きく改善する．`exchange_rate` は逆に悪化する
（ほぼランダムウォークなので履歴を増やしても雑音が増えるだけ）．

### 固定予算 2048 での比較

| | ETTh1 | ETTm2 | exchange_rate |
|---|---|---|---|
| 最良の参照なし | 0.5029 | 0.3633 | 0.1595 |
| 最良の実行可能な検索 | 0.5004 (**−0.5%**) | 0.3656 (**+0.6%**) | 0.1645 (**+3.1%**) |
| オラクル（完璧な検索） | 0.4934 (−1.9%) | 0.3553 (−2.2%) | 0.1616 (+1.3%) |
| 参考：短文脈96でのオラクル利得 | −17.4% | −26.3% | +32.8%（悪化） |

**3データセットとも，文脈予算を揃えたベースラインに対して検索はほぼ何も買えない．**
実行可能な検索が勝つのは ETTh1 の −0.5% だけで，ETTm2 と exchange_rate では負ける．
**完璧な検索ですら上限は 2.2%**（exchange では負ける）．

短文脈 96 で見えていたオラクル利得（−17.4%, −26.3%）は，
予算を揃えると −1.9%, −2.2% に潰れる．**約10倍の過大評価だった．**

### 短文脈では検索が有害になりうる

`exchange_rate` の 96 点文脈では，`raw` K=11 のチャネル正規化 MSE が
0.1595 → 5.06（チャネル中央値でも 0.107 → 0.345）まで悪化する．
チャネル4 が単独で 37.8 と壊れており，これは為替の水準ドリフトが大きく，
遠い過去の窓を生値で連結するとバックボーンの instance norm が破壊されるため．
**オラクルですら +32.8% 悪化する**ので，検索品質ではなく注入機構の問題である．

### 2つの失敗モード

| | ETTh1 / ETTm2 | exchange_rate |
|---|---|---|
| 直近の履歴 | 非常に有効 | 有害 |
| 検索が負ける理由 | **冗長**（答えは直近の履歴にある） | **有害**（答えがどこにも無く，注入は雑音） |
| オラクルの位置 | 長文脈にわずかに勝つ | 短文脈に大負け |

共通するのは**「そのまま連結する」注入機構が高くつく**こと．
ETT 系では文脈予算を食って冗長になり，exchange では系列の統計を壊して有害になる．
どちらも検索の中身ではなく容れ物の問題で，
中間発表の宿題②（選んだ事例をどう統合するか）が本丸だと示している．

### 粗利益とコストを分離する

固定予算の「純利益」は 2 つが混ざっている．検索が持ち込む利益と，
その席を作るために履歴を削ったコストである．
同じ履歴長で検索なしを走らせれば分離できる．

| ETTh1 | 履歴 | 同履歴で検索なし | オラクル | 検索の粗利益 | 連結の代償 | 純利益 |
|---|---|---|---|---|---|---|
| K=1 | 1872 | 0.5031 | 0.4985 | −0.9% | +0.0% | −0.9% |
| K=2 | 1696 | 0.5046 | 0.4960 | −1.7% | +0.3% | −1.4% |
| K=4 | 1344 | 0.5060 | 0.4934 | −2.5% | +0.6% | −1.9% |
| K=8 | 640 | 0.5243 | 0.5019 | **−4.3%** | +4.3% | −0.2% |

| ETTm2 | 履歴 | 同履歴で検索なし | オラクル | 検索の粗利益 | 連結の代償 | 純利益 |
|---|---|---|---|---|---|---|
| K=1 | 1872 | 0.3648 | 0.3618 | −0.8% | +0.4% | −0.4% |
| K=2 | 1696 | 0.3662 | 0.3590 | −2.0% | +0.8% | −1.2% |
| K=4 | 1344 | 0.3699 | 0.3553 | **−4.0%** | +1.8% | −2.2% |
| K=8 | 640 | 0.3889 | 0.3892 | −0.1% | +7.1% | +7.1% |

**検索の粗利益は約 4% ある．** 消えていたのではなく，
連結が文脈を食うコストで相殺されていた．
ETTh1 の K=8 では粗利益 4.3% に対して代償が 4.3% で，ちょうど帳消しになっている．

したがって正しい結論は「参照は無意味」ではなく，
**「参照は効いているが，連結という容れ物が利益を食い潰している」**である．
文脈予算を消費しない統合（cross-attention など）なら，
履歴 2048 を保ったまま検索窓を参照できるので，この粗利益を取り切れるはずである．
それが検証すべき仮説になる．

### この結果の適用範囲

- 本実装は Tire et al. の *Retrieval w/o Alignment* にあたる**素の連結**であり，
  cross-attention で参照する RAFT や，アダプタを学習する TimeRAF には
  「文脈予算を食う」という論点はそのまま当てはまらない．
- バックボーンは凍結 Chronos-Bolt，学習パラメータはゼロ，`pred_len` は 64．
- 3データセット，`--eval-stride 16`．

したがって主張は 2 つに分かれる．

1. **素の連結による RAF が報告してきた利得は，その大部分がベースラインの文脈不足に由来する．**
   文脈予算を揃えると純利益はほぼ消える．
2. **ただし検索の粗利益は約 4% 実在する．** 消しているのは連結という統合方式である．

したがって次に作るべきは「**文脈予算を消費しない統合**」であり，
そこで粗利益 4% が取れるかが，この路線が生きるかどうかの判定になる．
今日 encode / pool / select で得た改善（DPP，レジームプール，予測未来クエリ）は
文脈 96 点の土俵での結果なので，新しい統合の上で測り直すことになる．

## バックボーンを Chronos-2 に替える

`--chronos-model amazon/chronos-2` で切り替わる（`chronos-forecasting>=2.0`）。
連結の仕組みは一切変えていない。文脈が 2048 → **8192** に広がるので、
検索窓が予算に占める割合が下がる。パッチ長は 16 で同じ、NaN も欠測として扱える。

実装上の注意：MPS ではバッチ×文脈長が約 13 万点を超えると事実上停止する
（バッチ16・文脈8192 は 1.5 秒、バッチ32 は返ってこない）。文脈長からバッチを
自動計算し、実行は CPU を推奨（プロファイル上 CPU のほうが速い）。

### A. 参照なしで文脈長だけ伸ばす

| 文脈長 | Chronos-Bolt | Chronos-2 |
|---|---|---|
| 96 | 0.5842 | 0.6109 |
| 2048 | 0.5029 | 0.5004 |
| 8192 | 上限2048 | **0.4926** |

Chronos-2 は短文脈では Bolt に負け、長文脈で上回る。
**検索を一切せず履歴を 8192 読むだけで 0.4926**、
これは Bolt のオラクル K=11（0.4825）に迫る水準。

### B. 固定予算での検索（ETTh1 / qmean）

| 予算 | K | 履歴 | raw | predicted | future |
|---|---|---|---|---|---|
| 2048（参照なし 0.5004） | 4 | 1344 | +0.9% | +1.3% | **+1.2%** |
| | 8 | 640 | +2.6% | +2.7% | **+3.2%** |
| 8192（参照なし 0.4926） | 8 | 6784 | +0.1% | — | **−0.4%** |
| | 16 | 5376 | +0.1% | — | **−0.5%** |

- **予算 2048 では、オラクルすら損になる**（+1.2%、+3.2%）。
  Bolt では同条件で −1.9% だった。Chronos-2 は文脈を長く読むほど強い設計なので、
  履歴を手放す代償が Bolt より高くつく。
- **予算 8192 まで広げると符号は戻るが、完璧な検索で買えるのは 0.4〜0.5% だけ**。
  K を 8 → 16 に倍増しても −0.4% → −0.5% でほぼ動かない。

**基準線が強くなるほど検索の取り分は縮む**、という関係が一貫している
（Bolt 予算2048 で −1.9% → Chronos-2 予算8192 で −0.4%）。
容れ物を広げても、事例を読む設計になっていなければ意味がない。

### C. 短文脈で測ると「幻」が出る（バックボーン非依存）

| 文脈96の世界 | Chronos-Bolt | Chronos-2 |
|---|---|---|
| 参照なし K=0 | 0.5842 | 0.6109 |
| raw K=11 | 0.6051 (+3.6%) | 0.7017 (+14.9%) |
| **future オラクル K=11** | 0.4825 (**−17.4%**) | 0.3739 (**−38.8%**) |

短い文脈しか与えなければ、Chronos-2 では完璧な検索が **−38.8%** の劇的な利得に見える。
ところが同じモデルに履歴 8192 を与えるだけで 0.4926 に達し、
そこに検索を足しても 0.4% しか動かない。

**「文脈を絞ってから検索の効果を測る」という実験設計は、強いモデルほど大きな幻を生む。**
これは単一バックボーンの癖ではなく方法論の問題で、今回いちばん再利用価値のある知見。

### 示唆

Chronos-2 のオラクル（文脈96、K=11）0.3739 は、Bolt のどの条件よりも良い。
**事例を読む容れ物さえ正しければ、Chronos-2 は事例から多くを引き出せる余地がある**
——いまは連結が容れ物なので活かせていない、という読みになる。
Chronos-2 の入力口は `target / past_covariates / future_covariates / cat_covariate` のみで
事例のスロットが無く、group attention は「並列系列間の情報共有」であって
逐次的な実演を読む機構ではない。

したがって次は、事例を時間軸に置く設計を**学習可能セパレータで明示的に学習させる**
（TimesFM-ICF 相当のメタ学習）ことになる。

## 検索は「文脈を伸ばすこと」を内包するか

直近の履歴が最も有効なら、検索がそれを引けばよいので、
検索は文脈延長を内包するはずである。実装ではそうなっていない。
`--retrieval-mode recent`（クエリ直前の K 窓をそのまま使う）を入れると切り分けられる。
区切りなしで並べると連続した履歴に**厳密に一致する**（両方 0.5030 で確認済み）ので、
「中身は同じ・容れ物だけ違う」条件が作れる。

ETTh1、K=11、クエリ文脈 96、`--eval-stride 16`：

**同じ容れ物（qmean）で中身を変える**

| 連結する 11 窓の選び方 | MSE |
|---|---|
| オラクル（未来が近い窓） | **0.4825** |
| **直近の 11 窓（＝履歴そのもの）** | **0.5455** |
| `predicted`（予測未来で検索） | 0.5670 |
| 類似度で検索 | 0.6051 |

**同じ中身（直近 11 窓）で容れ物を変える**

| 容れ物 | MSE | 連続履歴比 |
|---|---|---|
| 区切りなし（＝連続した履歴 1856 点） | 0.5030 | — |
| `nan` 区切り | 0.5322 | +5.8% |
| `qmean` 区切り | 0.5455 | +8.4% |

読み取れること：

- **類似度検索は「直近を取るだけ」に負ける**（0.6051 対 0.5455）。
  最良の `predicted`（0.5670）ですら負ける。
  **recency はこれまで測っていなかったベースライン**で、どの検索手法もこれを超えていない。
- **中身が完全に同じでも、区切りを挟むだけで 5.8〜8.4% 悪化する**。
  容れ物は本当に損をしている。
- 類似度検索（0.6051）と連続履歴（0.5030）の差 0.1021 は、
  **選択の損 0.0596（58%）＋ 容れ物の損 0.0425（42%）** に分解できる。

したがって答えはこうなる。**検索が文脈延長を内包するのは、
「連続した直近を区切りなしで引く」縮退した場合だけで、そのときそれは検索ではなく文脈延長である。**
不連続な窓を境界付きで並べる本来の検索は、必ず容れ物の損を払う。

ただし**オラクル 0.4825 は連続履歴 0.5030 を 4.1% 下回る**ので、
検索の中身が recency より良くなりうること自体は成立している。
条件は「容れ物の損（約 8%）を上回るだけ中身が良いこと」で、
オラクルはかろうじてそれを満たしている。現行の検索器はまったく満たしていない。

## 検索DBを「クエリ以前のすべて」に広げる

これまで検索DBは train split に固定していた。クエリ自身の直近は DB に入っていないので、
「直近が最も有効なら検索が直近を引けばよい」が構造的に不可能だった。
`--retrieval-split past` は、クエリ文脈が始まる前に終わるすべての窓を候補にする
（重なる窓は除外されるので漏れはない）。stride 1 では
クエリ直後の窓が最近傍を独占するため、over-search では切れない。
faiss の `IDSelectorRange` で探索そのものを打ち切っている。

ETTh1、K=11、クエリ文脈96、qmean：

| | DB=train | DB=過去すべて |
|---|---|---|
| 類似度で検索 | 0.6051 | **0.5811** |
| オラクル | 0.4825 | **0.4615** |

両方 4% 前後改善する。**DB の制約は実在するハンデだった。**
オラクル 0.4615 は連続した履歴（0.5030）を **8.2%** 下回り、
これまでの 4.1% から倍増する。検索の中身が文脈延長を上回りうることは、より強く成立する。

ただし**クエリ文脈が長い条件では DB 拡張はほぼ効かない**（固定予算2048、K=4/履歴1344 で
オラクル 0.4934 → 0.4931）。長い文脈には直近が既に入っているので、
検索で足しても重複になるため。**検索の取り分は「直近でない中身」からしか出ない。**

## 連結は壊れやすい（測定上の重大な注意）

入力長をわずかに変えて感度を測ると、検索の有無で挙動がまったく違う。

| クエリ文脈 | 総入力長 | raw K=11 | オラクル K=11 |
|---|---|---|---|
| 96 | 2032 | 0.6051 | **0.4825** |
| 104 | 2040 | 0.5849 | **0.5426** |
| 112 | 2048 | 0.5738 | **0.5123** |

| 参照なしの文脈長 | MSE |
|---|---|
| 1856 | 0.5030 |
| 1864 | 0.5030 |
| 1872 | 0.5031 |

**参照なしは 8 点動かしても 0.0001 しか動かない。連結を入れると最大 12% 動き、しかも非単調。**
事例の境界とパッチ境界（16点）の相対位置に強く依存していると考えられる。

含意は2つある。

1. **連結という容れ物は、損をするだけでなく不安定でもある。**
   これは「容れ物が問題」という診断をさらに補強する。
   学習可能セパレータで境界を明示的に学習させる動機がここにもある。
2. **総入力長が異なる条件どうしを比べてはいけない。**
   本 README の固定予算の表はすべて総入力長 2048 に揃えてあるので表内の比較は成立するが、
   総長 2032 の K=11 の結果と直接並べるときは、この感度を上回る差かどうかを確認すること。
   大きな効果（文脈 96→2048 の 14%、recency 対 類似度の 11%、容れ物の損 8%）は
   この感度を明確に上回る。小さな効果（0.5%、1.9%）は上回らない。

## 正しい土俵での再評価

今日わかった 3 つの問題（DB が train 固定・recency 基準線の欠落・入力長への感度）を
すべて潰した条件で、これまでの全手法を測り直す。

**統一条件**：ETTh1 / K=11 / クエリ文脈96 / 区切り qmean / `--retrieval-split past` /
総入力長 2032（全条件で同一）/ `--eval-stride 16`

| 手法 | MSE | recency比 | 履歴比 |
|---|---|---|---|
| **【基準線】連続した履歴（検索なし）** | **0.5031** | **−7.8%** | — |
| **【基準線】recency（直近11窓）** | 0.5455 | — | +8.4% |
| *encode 軸（selector=topk）* | | | |
| `raw`（類似度・生値） | 0.5811 | +6.5% | +15.5% |
| `zscore`（形だけ） | 0.5886 | +7.9% | +17.0% |
| `spectral`（周波数） | 0.6560 | +20.2% | +30.4% |
| `learned`（対照学習） | 0.5748 | +5.4% | +14.3% |
| `predicted`（予測未来） | 0.5678 | +4.1% | +12.9% |
| *select 軸（dpp w=0.75, pool100）* | | | |
| `raw` + dpp | 0.5460 | +0.1% | +8.5% |
| `predicted` + mmr | 0.5643 | +3.4% | +12.2% |
| `predicted` + dpp | 0.5465 | +0.2% | +8.6% |
| `learned` + dpp | 0.5682 | +4.2% | +12.9% |
| *オラクル（実行不能）* | | | |

読み取れること：

- **recency を下回った実行可能な手法はゼロ。** 最良の `raw + dpp`（0.5460）と
  `predicted + dpp`（0.5465）は recency（0.5455）と同点で、上回ってはいない。
- **DPP は全手法を recency の水準まで引き上げるが、そこで頭打ちになる。**
  多様性を上げることは「平均に寄せる」ことに近く、recency が与えるものに収束する。
- **どの実行可能な手法も、検索しない連続履歴（0.5031）に大きく負ける。**
- `future + dpp`（0.4683）は `future` 単体（0.4615）より悪い。
  「検索が良いほど多様性は不要」という関係はここでも成立する。

**したがって現状はこうである。**

| | MSE | 意味 |
|---|---|---|
| オラクル | 0.4615 | 検索の天井 |
| 連続履歴 | 0.5031 | 検索しない場合。天井との差 8.3% が検索の取り分 |
| recency | 0.5455 | 検索手法が最低限超えるべき線 |
| 実行可能な最良 | 0.5460 | recency と同点。**天井までの 15.5% を1つも取れていない** |

検索の価値（8.3%）は実在するが、**それを取りにいく検索器がまだ存在しない**。
選択の余地は 15.5% あり、これは中間発表の宿題①②そのものである。
以前の「参照なし K=0 = 0.5842 を 5.1% 下回った」という主張は、
弱い基準線に対するものだったので取り下げる。

## 文脈内学習は起きていない

Min et al. (2022) が LLM で行った検証を，そのまま持ち込む。
検索窓の**未来だけ**を壊し、性能が動くかを見る（`--example-ablation`）。
文脈は検索が照合した部分、未来は「そのあとこうなった」を運ぶ部分である。

ETTh1、K=11、DB=past：

| 壊し方 | raw 類似度 | オラクル |
|---|---|---|
| 壊さない | 0.5811 | 0.4615 |
| **K個の未来を入れ替え**（対応だけ壊す） | **0.5731** | **0.4623** |
| 無関係な未来に差し替え | 0.6408 | 0.5928 |
| 未来を消す（NaN） | 0.5732 | 0.5307 |

- **入れ替えても変わらない**（オラクルで +0.2%）。
  「この文脈のあとにこの未来が来た」という対応関係は使われていない。
- raw に至っては**未来を消したほうが良い**（0.5811 → 0.5732）。
- 一方オラクルは未来を消すと 15% 悪化するので、未来そのものは効いている。

したがって機構は「事例から写像を学ぶ」ことではなく、
**ありうる未来の分布を注入すること**である。
これは Min et al. の「入力とラベルの対応は重要でなく、ラベルの分布が効く」と一致する。

## 帰結：検索窓の文脈は死荷重だった

対応が使われないなら、検索窓の文脈部分（160点中96点、**60%**）は
予算を食うだけである。`--example-part future` で未来だけを渡す。

**総入力長 2032 に統一、ETTh1、DB=past、qmean：**

| K | 履歴 | raw | predicted | オラクル |
|---|---|---|---|---|
| 0（検索なし） | 2032 | 0.5031 | — | — |
| 4 | 1712 | 0.4993 | 0.5019 | 0.4944 |
| 6 | 1552 | 0.4989 | 0.5026 | 0.4917 |
| **11** | 1152 | **0.4972** | 0.5052 | 0.4866 |
| 16 | 752 | 0.4977 | 0.5078 | 0.4774 |
| 20 | 432 | 0.5119 | 0.5237 | 0.4697 |

**同じ予算で、実行可能な検索が初めて「検索なし」を下回った**（0.4972 対 0.5031、−1.2%）。
しかも最も素朴な類似度検索（`raw`）である。

参考として、窓ぜんぶを渡す従来構成では raw 0.5811 / オラクル 0.4615、
recency 0.5455、連続履歴 0.5031 だった。

その他の観察：

- **オラクルは履歴なしが最良**。未来だけ K=11、総長 976（予算の 48%）で **0.4454**。
  検索の天井はこれまでの 0.4615 から大きく上がった。
- **`predicted` が最下位に転落する**。窓ぜんぶのときは raw に勝っていた（0.5678 対 0.5811）のに、
  未来だけにすると全 K で負ける。なめらかな未来ばかり集める害が、
  文脈という緩衝材を失って直接効いている。
- オラクルは K を増やすほど良くなり、raw は K=11 付近が最適。
  検索品質が低いほど履歴に頼るべき、という関係。

**これまで予算の 60% を、モデルが読んでいない部分に払っていた。**

## プラセボを超える：融合（そして CA の失敗）

### 発端：我々の推定量は Nadaraya-Watson だった

上位 K 件の未来を平均するのは**局所定数（Nadaraya-Watson）推定**である。
そのバイアスは J(x̄ − x_q)：近傍の文脈はクエリから見て偏り、
コーパスの主要部へ引かれるので、平均した未来も同じだけ引かれる。
**「平均への回帰」と呼んでいたものは、この既知のバイアス項だった。**

古典的な解が **Constructed Analogue**（van den Dool 1994）。候補の**文脈**の
線形結合がクエリ文脈を再構成するように重みを解き、同じ重みを未来に適用する。

```
w = argmin ||Σ w_k x^(k) − x_q||² + λ||w||²      y_CA = Σ w_k y^(k)
```

局所線形なら一次バイアスが消え、重みが負を取れるので凸包の外へ出られる
（どの検索窓より鋭い予測を作れる）。

**直接予測としては効く**（ETTh1、val で λ・M を選択）：
CA 0.5540 に対し単純平均 top-11 は 0.6346。**−12.7%**。

### しかし end-to-end には伝わらない

| 注入経路 | 検索推定量の改善 | end-to-end |
|---|---|---|
| 文脈へ連結 | −16% | −0.1%（0.4972 → 0.4968） |
| 予測を直接融合 | −12.7% | **+0.5%（悪化）** |

**検索側の推定量をいくら良くしても最終性能に伝わらない。経路を変えても同じ。**
今日の実験で最も再現性のある現象である。

### 融合そのものは効く

```
ŷ = (1 − α)·Chronos(履歴2032) + α·y_ret
```

**すべてのハイパーパラメータを検証 split で選び、テストで評価：**

| 手法 | 選んだ設定 | val | test | プラセボ比 |
|---|---|---|---|---|
| 融合なし（Chronos 単体） | — | 0.3957 | 0.5031 | +1.4% |
| **プラセボ** | — | — | **0.4963** | — |
| **融合・単純平均 top-11** | α=0.20 | 0.3879 | **0.4923** | **−0.8%** |
| 融合・Constructed Analogue | M=200 λ=3 α=0.35 | 0.3828 | 0.4946 | −0.3% |
| オラクル注入（実行不能） | — | — | 0.4866 | −2.0% |

**実行可能な手法として初めてプラセボを超えた**（0.4923）。
ただし勝っているのは**単純平均のほうで、CA は負ける**。

**注意（一度誤った点）**：当初 CA が 0.4874 でプラセボを超えたと報告したが、
これは λ をテスト集合で選んでいた。val で選ぶと λ=3 が選ばれ、
テストでは λ=30 が良いという**期間をまたいだ不安定さ**があり、CA の優位は消える。
ハイパーパラメータは必ず val で固定してから評価すること。

### 位置づけ

この融合は**文脈注入型 RAF ではなく事後融合型**であり、
**TS-Memory**（arXiv:2602.11550）の Stage 1 + 融合とほぼ同一である：

| | TS-Memory | 本実装 |
|---|---|---|
| 検索側の集約 | 距離ソフトマックス重みの経験分位点（式7-8）＝局所定数 | 単純平均（同種） |
| 検索窓の文脈 | 検索後に破棄 | 同じ |
| 融合 | 分位点ごとの線形補間、α は検証 split で調整（式22） | 同じ |
| 学習 | Stage 2 でアダプタに蒸留 | なし |

**したがって融合による勝ちに新規性はない。** CA という差分は、
honest な評価では効かなかった。

## なぜ改良が伝わらないのか（機構の解明）

検索側の推定量を良くしても end-to-end が動かない、という現象が
文脈注入でも直接融合でも再現した。線形結合の理論で完全に説明できる。

2 つの予測を混ぜたときの最適な誤差は

```
MSE* = (V1·V2 − C²) / (V1 + V2 − 2C)
```

で、相手の**精度 V2 だけでなく誤差の共分散 C にも依存する**。実測（ETTh1 test、正規化）：

| 検索側の推定量 | 単体 MSE (V2) | Chronos 誤差との相関 | 最適 α | 結合 MSE（理論） |
|---|---|---|---|---|
| recency 直近11窓 | 1.3588 | **0.536** | 0.06 | 0.4994 |
| 単純平均 top-11 | 0.6346 | 0.802 | 0.22 | 0.4922 |
| CA λ=3 | 0.5540 | 0.892 | 0.28 | 0.4940 |
| CA λ=30 | 0.5306 | **0.891** | 0.38 | 0.4867 |
| Chronos 単体 | 0.5031 | — | — | — |

理論値（0.4922 / 0.4867）は実測（0.4923 / 0.4874）とほぼ一致する。

**CA は「Chronos と同じことをする」ことで精度を上げていた。**
単純平均 ρ=0.802 → CA ρ=0.891。局所線形の外挿はバックボーンが内部で既に行う計算なので、
精度が上がった分だけ相補性が消える。差し引きゼロ。

**これが今日の全失敗を説明する。** encoder の改良も、予測未来を鍵にすることも、CA も、
すべて「モデルに似せる」方向だった。似せるほど相補性が消える。

## 残差アナログ：相補的だが予測不能

相補性を設計に組み込む最も直接的な方法として、
DB に未来ではなく**その時点での Chronos の予測誤差**を格納し、
`ŷ = f + β·r̂` とする（気象学の analog + Kalman 誤差補正に対応）。

train / val / test 直前履歴で Chronos 予測を作り、残差 DB を構築した。

| | val | test |
|---|---|---|
| 融合なし | 0.3945 | 0.5031 |
| 残差アナログ（β=0.45） | 0.3860 | **0.5048（悪化）** |
| 未来アナログ（β=0.25） | 0.3813 | **0.4899** |

**狙いどおり相補的になった**（誤差相関 0.211 → **0.096**）。しかし失敗した。

| | 正規化分散 |
|---|---|
| 実際の残差 | 0.5031 |
| 検索した残差 r̂ | 0.0761 |
| r̂ と実残差の相関 | **+0.096** |

**残差はほとんど当てられていない。** 残差とは「バックボーンが説明できなかった成分」なので
定義上ほぼ雑音であり、相補的なのは当然で、同時に予測不能でもあった。
足すと分散だけ増える。

**結合の式は C が小さいことだけでなく V2 も小さいことを要求する。
相補的かつ予測可能でなければならない。** 残差は前半しか満たしていない。

## DB は間引いたほうが良い

副産物として、検索 DB の粒度に強い影響があることが分かった（ETTh1 test、β=0.20 固定）：

| DB stride | 候補数/ch | アナログ単体 | 融合後 |
|---|---|---|---|
| 8 | 1,760 | **0.5921** | **0.4910** |
| 4 | 3,520 | 0.5869 | 0.4904 |
| 2 | 7,040 | 0.5949 | 0.4906 |
| 1 | 14,080 | 0.6346 | 0.4923 |

**stride 1 では重なった near-duplicate を K 件引いてしまい、実効的な独立事例数は 2 程度しかない。**
間引くほうが良い。DPP（多様性）が唯一まともに効いた理由もこれで説明できる。

β を val で選んだ最良は **0.4899**（未来アナログ、DB は train@8 + val@8 + 直近履歴@4）。
プラセボ 0.4963 を 1.3%、検索なし 0.5031 を 2.6% 下回り、オラクル注入 0.4866 まで残り 0.7%。

## オラクル上限は達成可能な伸びしろではない

「バックボーンが見られない情報を使え」という設計原理から 2 つ試し、
どちらも失敗した。

### B. 多チャネル検索：相補性が生まれない

照合に使うチャネルを変える（ETTh1, DB stride 8, K=11）：

| 照合チャネル | 単体 MSE | Chronos誤差との相関 | test |
|---|---|---|---|
| 当該チャネルのみ（従来） | 0.7168 | 0.784 | 0.4919 |
| 全 7 チャネル | 0.5652 | 0.825 | 0.4923 |
| **他 6 チャネルのみ** | 0.5846 | **0.806** | 0.4919 |

**当該チャネルを一切見なくても相関は下がらない。**
ETTh1 はチャネル間相関が高く、他チャネルで照合してもほぼ同じ窓が選ばれる。
「バックボーンが見られない情報」という原理は正しくても、
ETTh1 の他チャネルは実質的に同じ情報だった。

### A. クエリごとの融合重み：上限は巨大、掴む手が無い

| 方式 | val | test | β との相関 (val/test) |
|---|---|---|---|
| 融合なし | 0.3945 | 0.5031 | — |
| 一律 β=0.25 | 0.3841 | **0.4903** | — |
| **クエリ毎オラクル β（上限）** | 0.3199 | **0.4342** | — |
| 分位点幅で 2/3/5 ビン | — | 0.4916 / 0.4935 / 0.4929 | — |
| Ridge（文脈96点＋5特徴で学習） | 0.3869 | 0.4904 | −0.002 / +0.113 |
| 勾配ブースティング | 0.3888 | 0.4932 | +0.041 / +0.028 |
| **対照：ターゲットをシャッフル** | 0.3867 | **0.4927** | — |

上限 0.4342 は注入オラクル 0.4866 すら下回る。最適 β は
**0 が 41%、1 が 15%** という二値的な分布で、情報量は大きい。
それでも観測可能な特徴（分位点幅、検索結果の内部ばらつき、最近傍距離、
Chronos と検索の不一致、文脈の荒さ）との相関はすべて ±0.15 以内、
7,400 事例で学習しても相関はほぼゼロで、勾配ブースティングは
**シャッフル対照より悪い**。

### 4 回同じ形で失敗した

| 課題 | オラクル上限 | 掴めたか |
|---|---|---|
| 多様性 w をクエリ毎に | −11% | 乱数対照と同等 |
| 事例の選択 | −15% | 全代理指標が失敗 |
| 融合 β（手作り特徴） | −11% | 相関ほぼゼロ |
| 融合 β（学習） | −11% | シャッフル対照と同等 |

共通する理由が見える。

> **測ったオラクル上限は、すべて「実現した未来」または「実現した誤差」を条件にしている。**

- 検索のオラクル ＝ 真の未来を知っている
- 最適 β ＝ どちらの誤差が小さいかを知っている
- 残差アナログ ＝ 誤差そのものを当てようとした（r̂ と実残差の相関 +0.096）

**自分の誤差を予測できるモデルは、その分を既に予測へ織り込んでいるはずである。**
だから原理的に残らない。

**方法論上の含意**：RAF のオラクル上限は、達成可能な伸びしろの尺度として使えない。
実現値を条件にした量なので、到達不能な成分を含む。
本調査自身、朝に「オラクルが 19.5% 良いから検索を改良すべき」と読んで一日を費やしたが、
その 19.5% の相当部分はそもそも到達できない量だった可能性が高い。

## バックボーンを替えると結論が変わる：Chronos-2

ここまでの診断はすべて Chronos-Bolt 上で行った。同じ ablation を Chronos-2 で走らせると、
**いくつかの結論が逆転する**。既定のバックボーンは Chronos-2 に変更した
（MPS はメモリ崖があり CPU のほうが速いので、chronos-2 選択時は自動で CPU に落とす）。

### ICL ablation

| 壊し方 | Bolt raw | C2 raw | Bolt オラクル | C2 オラクル |
|---|---|---|---|---|
| 壊さない | 0.5811 | 0.6268 | 0.4615 | **0.3397** |
| K個の未来を入れ替え | 0.5731 | 0.6106 | 0.4623 | 0.3491 |
| 無関係な未来に差替 | 0.6408 | **1.6348** | 0.5928 | **1.1299** |
| 未来を消す | 0.5732 | 0.6267 | 0.5307 | 0.5671 |

**Chronos-2 は注入内容を強く信じる。** 未来を消すとオラクルは +67%（Bolt は +15%）、
無関係な未来に差し替えると +233%（Bolt は +28%）悪化する。
Bolt は事例をほとんど無視していた、という言い方もできる。

**ただし対応関係は依然ほぼ使われない**（入れ替えによる悪化は Bolt +0.2% に対し C2 +2.8%）。
一桁大きいが小さい。パッチ化により勾配降下としての ICL が成立しないという議論は
Chronos-2 でも成立している。

### 基準線一式（K=11・クエリ文脈96・総長2032）

| | MSE | QL |
|---|---|---|
| 参照なし・文脈96 | 0.6109 | 0.2127 |
| 参照なし・文脈2032 | 0.5007 | 0.1887 |
| recency 直近11窓 | 0.5247 | 0.1978 |
| **プラセボ（雑音・クエリ統計）** | **0.7078** | 0.2476 |
| 雑音・検索した統計 | 0.7379 | 0.2502 |
| **時間順序シャッフル** | **0.7528** | 0.2478 |
| **raw 類似度** | **0.6268** | 0.2205 |
| **オラクル** | **0.3397** | **0.1597** |

**Bolt と正反対のことが 3 つ起きる。**

| | Bolt | Chronos-2 |
|---|---|---|
| プラセボ | 参照なしより**良い**（副作用が助けになる） | 参照なしより**悪い**（害） |
| 波形を壊す（shuffle-time） | 無害〜やや改善 | **+20% 悪化** |
| raw vs プラセボ | raw の負け | **raw が 11% 勝つ** |

**Chronos-2 では検索した波形が実際に使われている。**
「波形は使われず統計だけが効く」という診断は Bolt 固有だった。

### 未来だけにすると Chronos-2 は壊れる

| | 未来だけ＋履歴1152 | 未来だけ・履歴なし(976) |
|---|---|---|
| プラセボ | 0.5118 | — |
| raw | 0.5051 | 0.8392 |
| オラクル | 0.5172 | 0.9026 |

Bolt では「検索窓の文脈は死荷重、捨てると改善」だったが、Chronos-2 では壊滅する。
文脈を剥いだ 64 点のブロックは不連続な飛びに見え、強く信じる分だけ害になるらしい。
（未来だけ＋履歴でオラクルが raw より悪いのは奇妙で、未解明。）

### 何が変わり、何が変わらないか

**変わった**：容れ物についての診断（波形は使われない／未来だけでよい）は Bolt 固有。
Chronos-2 では窓ぜんぶを渡すべきで、波形も効く。

**変わらない**：
- 対応関係は依然ほぼ使われない（+2.8%）
- **実行可能な検索は依然として履歴に負ける**（0.6268 対 0.5007）

**そして天井が跳ね上がった**：

| | 実行可能（raw） | オラクル | 差 |
|---|---|---|---|
| Bolt | 0.5811 | 0.4615 | 21% |
| **Chronos-2** | 0.6268 | **0.3397** | **46%** |

0.3397 は参照なし 8192 文脈（0.4926）を 31% 下回る。
**「検索の価値はほとんど無い」という結論は、天井の低いバックボーンで測っていたことによる。**
変わったのは賞金の額であって、そこへ至る手段が見つかっていない状況ではない。

### 分位点損失でも結論は同じ

`evaluate.py` に分位点損失（全 9 分位点のピンボール損失をチャネル標準偏差で正規化）を追加し、
ICL ablation・encode/select 軸・予算配分をすべて測り直した。
**順位変動はすべて 0.0001〜0.0006 の同着レベル**で、結論は変わらない。
「MSE が検索の価値を隠していた」という仮説は否定された。
本調査の結論が MSE のアーティファクトではないことの確認にはなっている。

## 出力

`results/<dataset>_c<seq>_h<pred>_k<K>_<metric>` を接頭辞に3ファイル．

**`.parquet` — 予測表**（1行 = 1窓）

| 列 | 意味 |
|---|---|
| `channel` | 列名 |
| `window` | そのチャネル内の窓番号 |
| `start` | 評価split内での窓の開始位置 |
| `pred_q0.1_0` … `pred_q0.9_63` | 9分位点 × 予測長の予測値（生スケール） |
| `true_0` … `true_63` | 実測値 |

点予測は `pred_q0.5_*`（中央値）．指標は計算していないので，MSE でも MASE でも WQL でも後から出せる．

**`_retrieval.parquet` — 検索ログ**（1行 = 1件の検索結果）

| 列 | 意味 |
|---|---|
| `channel`, `window`, `start` | どのクエリか |
| `rank` | 何番目に近いか（0 が最近傍） |
| `db_index` | 検索DB配列内のindex |
| `db_start` | 検索split内での窓の開始位置 |
| `distance` | 小さいほど近い（指標によらず統一） |

`db_start` から元の窓を復元できるので，どの事例を引いた結果どう外したかを後から追える．

**`_args.json` — 実行条件**．ファイル名に入らない引数（`--concat-order`，`--retrieval-split` など）もすべて記録される．
